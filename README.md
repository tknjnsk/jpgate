# JPGate

日本国内でしか買えない商品の**予約開始・抽選開始・再販を検知して英語で通知する**ツール。

代行業の集客導線として作っている。通知そのものが商品説明になるよう、
各アイテムに「海外の客が越えられない関門（ゲート）」を必ず添える。

```
jpgate doctor    各経路が生きているか検査（スクレイパーは静かに嘘を返すので必須）
jpgate scan      走査してイベントをDBに貯める
jpgate notify    未通知イベントを Discord へ（既定は dry-run、送るには --no-dry-run）
jpgate publish   site/index.html と site/x_queue.txt を作り直す
jpgate run       scan → notify → publish（定期実行用）
```

パッケージは未インストールなので **`PYTHONPATH=src`** が必要。
Discord Webhook は `config.yaml` ではなく環境変数 `JPGATE_DISCORD_WEBHOOK`。

## なぜゲートが中心にあるのか

この事業の堀は「日本人だから」ではない。それでは検証できないし、値段も付かない。
値段が付くのは、**海外の客がどう頑張っても越えられない具体的な関門**があるときだけ。

| キー | 関門 | 根拠の取り方 |
|---|---|---|
| `G1_JP_PHONE` | 日本の携帯番号でSMS認証 | 抽選販売アイコン（会員登録が必須） |
| `G2_JP_ADDRESS` | 国内配送先のみ | サイトのポリシー（`config.yaml` に宣言） |
| `G3_JP_PAYMENT` | 国内発行の決済手段 | 抽選販売アイコン |
| `G4_IN_STORE` | 実店舗での抽選・受取 | 未実装（店頭抽選のソースを足すとき） |
| `G5_JP_ID` | 日本の本人確認書類 | 未実装（メルカリ等を足すとき） |

ゲートの根拠は2つに限られる。

- **アイテム由来**: 販売元が自分で出している機械可読なフラグ。現状は抽選販売アイコンのみ。
- **ソース由来**: `config.yaml` の `gates:` 宣言。`evidence`（根拠）と `verified_on`（確認日）が
  **必須**で、空だと `SourceGate.from_config` が例外を投げる。根拠を書けないものは宣言できない。
  確認日が180日を超えると `doctor` が警告する（サイトのポリシーは黙って変わるため）。

どちらの根拠も無ければ `UNKNOWN` であって「ゲート無し」ではない。
**UNKNOWN の商品には代行のCTAを出さない**。越えられる関門を「越えられない」と売ることになるため。

## 判定に効く「破れない制約」

いずれも実データで事故を確認してから入れている。

- **イベントは「在ること」からしか作らない。「無いこと」からは作らない。**
  一覧の先頭数ページしか見ないので、載っていない＝終了ではない。この規則があるので、
  走査ページ数を自由に動かしても誤通知が増えない。
- **`ok=False` の走査は一切反映しない。** 落ちた走査を反映すると、取れなかった商品が
  「消えた」ように見える。失敗は seed としてもカウントしない。
- **初回成功走査は seed でイベント0件。** でないと初回に数万件の「予約開始」を撒く。
- **状態判定は終了系を先に見る。** 抽選販売アイコンは**終了後も残る**ので、
  先に `ITEM_LOT_SALES` を見ると終わった抽選を受付中として通知する。
- **未知アイコンは握り潰さず報告する。** 新しい状態を「状態なし＝販売中」と読むのが
  一番危険なため。実際にこれで `ITEM_SALE_END`（販売終了）を検出した（下記）。
- **掲載0件のとき公開ページを書き換えない。** 走査が壊れているときに
  「在庫ゼロ」に見えるページを自分で作らないため。

テストは値の妥当性ではなく、この制約群が破れていないことを検証している（`tests/test_jpgate.py`）。

## プレミアムバンダイ 取得経路の事実（2026-08-17 実測）

- **一覧ページは素のHTTPで実HTMLを返す。**
  `https://p-bandai.jp/<shop>/list-da<件数>-n<オフセット>/`
  robots.txt が禁じているのは `/search/` `/mypage/` 等でこの一覧は対象外。
  sitemap-index.xml からも同種の一覧URLが公開されている。既定の並びは新着順。

- **商品詳細 `/item/item-<id>/` はHTMLが返らない。**
  中身の無いチャレンジシェル（metaタグすら無い）が返る。Playwright のヘッドレスも
  「アクセス制限」で弾かれた。**詳細ページに依存する設計にしてはいけない。**
  幸い一覧カードに ID・商品名・価格・状態アイコン・発送月が全部載っているので不要。

- **User-Agent が素だとトップページすらチャレンジになる。**
  `Mozilla/5.0` だけでは通らない。ブラウザ相当のフルUAが必須。

- **エンコーディングは Shift_JIS。** UTF-8 で読むと日本語が全部壊れる。

- **存在しないショップ名を渡すと 404 にならずトップページが返る。**
  `kids` で 157KB のトップページを掴んだ。商品0件を「全部売り切れ」と読むと
  全商品に再販通知を出しかねないので、パースは必ず `_assert_listing_page()` を通す。

- **`gundambase` と `fashion` はカテゴリ階層が要る別URL形式**
  （`gundambase/a<N>/list-...`）なので現在の shops リストでは動かない。未対応。

### アイコン語彙（販売元が出す機械可読なフラグ）

状態を決めるのはこれだけ。文章からの推測は一切していない。

| アイコン | alt | 扱い |
|---|---|---|
| `ITEM_LOT_SALES` | 抽選販売 | 状態: 抽選受付中 ＋ **G1/G3 ゲートの証拠** |
| `ITEM_RESERVE` | 予約 | 状態: 予約受付中 |
| `ITEM_RESERVE_END` | 予約終了 | 状態: 終了 |
| `ITEM_SALE_END` | 販売終了 | 状態: 終了 |
| `ITEM_OUT_OF_STOCK` | 在庫無し | 状態: 在庫無し |
| `ITEM_IN_STOCK` | 在庫商品 | 属性（状態を変えない） |
| `ITEM_ORDER_PRODUCTION` | 受注生産商品 | 属性 |
| `ITEM_DEADLINE` | 締切間近 | 属性 ＋ 締切イベント |
| `DELIVERY_EACH` / `ITEM_SDGS` | 個別配送 / SDGs | 属性 |
| `RESERVE_YYYYMM` | 配送 | 発送月（カレンダーの並び順） |

`ITEM_SALE_END` `ITEM_IN_STOCK` `ITEM_ORDER_PRODUCTION` の3つは、初回の20ページ
サンプルには**現れず**、本走査の未知アイコン報告で発見した。とくに `ITEM_SALE_END` は
知らないうちは「状態アイコンなし＝販売中」と読まれており、**販売終了品を公開ページに
買えるものとして並べていた**（取り込みで掲載150→145件に減ったのがその修正）。
未知アイコンを握り潰さない仕掛けが実際に事故を止めた記録。

## 商品名の英語化について

機械翻訳は使わない。この界隈の商品名はブランド名・シリーズ名・キャラ名の連結で、
翻訳するとかえって検索できなくなる（`METAL BUILD` を「金属製ビルド」にする類の事故）。

`data/glossary.yaml` による置換だけを行い、**置換できなかった部分は日本語のまま残す**。
訳せたふりをしない。訳出率が `min_translation_coverage` を下回ると、通知に原題を併記する。

用語集に載せる英語は「訳語として正しい語」ではなく
**海外コレクターが実際に検索に使う綴り**を選ぶこと。eBay で当たる綴りが正解。

## X（旧Twitter）について

API が有料なので自動投稿しない。`site/x_queue.txt` に投稿文を吐いて手で貼る。
自動化できていないことをキューとして可視化しておくほうが、投稿が止まったときに気づける。

## 事業側の前提（コードでは解決できない）

- **チケットは対象外。** 興行チケットの有償譲渡は不正転売禁止法に触れる。代行の建て付けでも危険。
- **新品の購入代行に絞れば古物商許可は原則不要**（所有権が最初から客に帰属する形）。
  中古（駿河屋・メルカリ）を扱い始めた時点で許可が要る領域に入る。
- **プレミアムバンダイは規約で転売目的の購入を禁止**している。代行は建て付けが違うが、
  アカウント凍結リスクは残る。事業リスクとして持つべきで、隠す前提の設計にはしない。
- リチウム電池・食品・ワシントン条約対象品は輸出側で弾かれる。
- 姉妹プロジェクト [KujiRadar](../KujiRadar/) は「自分で仕入れて自分で売る」形で、
  eBayのセリングリミット（月10品／90日クロック）が律速だった。**代行はこの制約を
  構造的に回避する**（客が直接払い、個人として発送するので出品枠を使わない）。

## 公開とアフィリエイト

サイト: **https://tknjnsk.github.io/jpgate/** （GitHub Pages、`main` の `/docs`）

更新は `powershell -ExecutionPolicy Bypass -File deploy.ps1`
（scan → notify → publish → commit → push）。

**走査は必ずこのPCから実行すること。** GitHub Actions のランナーはデータセンターIPで、
プレミアムバンダイは非ブラウザからのアクセスをチャレンジで弾く（素のUAではトップページ
すら通らないことを実測済み）。クラウドで走らせると静かに0件になる。
Actions に任せてよいのは生成済み `docs/` の配信だけ。

### ゲートが収益経路を決める

| 状態 | 海外の客に残る経路 | 出すもの |
|---|---|---|
| 抽選（G1） | **代行しかない** | 自社代行のCTA。**アフィリを出さない** |
| 終了 / 売り切れ | 二次流通のみ | eBay・Amazon の検索リンク |
| 予約受付中・販売中 | 一次流通が生きている | 公式へのリンクのみ |
| UNKNOWN | 不明 | 何も出さない |

抽選を他社の転送代行に流すのは自分の堀を売ることに等しい。転送代行は
アカウント作成のSMS認証を越えられないので、そもそも代行できない領域。

### 直リンクではなく検索リンクにしている理由

商品への直リンクは「この出品はその商品だ」と断言することになる。日英の商品同定は
[KujiRadar](../KujiRadar/) を最も苦しめた問題で、裸の採番は世界的に非ユニーク
（`15/89` がタイヤに、`N4/N25` がフォトカプラに当たる）。断言した先が別商品だと
こちらが嘘をついたことになる。**検索リンクは何も断言しない。**
収益は多少落ちるが、このサイトの資産は信用なので、そこを削って得る収益は割に合わない。
同じ理由で「$XX で買えます」という価格表示もしない。

### アフィリエイトIDの入れ方

`JPGATE_EBAY_CAMPAIGN_ID` と `JPGATE_AMAZON_US_TAG`（`config.yaml` より優先）。
**空のあいだリンクは1本も生成されない。** 審査前にリンクを出すと規約違反になるため。

順序に制約がある。**eBay Partner Network も Amazon アソシエイトも審査に実在する
サイトが必要**なので、「公開 → 中身が溜まる → 申請 → IDを入れる」の順でしか進めない。
Amazon は登録後180日以内に売上が無いとアカウントが閉じるので、流入が出てから申請する。

開示文（`affiliate.DISCLOSURE_EN`）はIDが入ると自動でページ下部に出る。
景品表示法のステマ規制（2023年10月〜）と各プログラムの規約の両方で必須。
リンクには `rel="sponsored nofollow"` を付けている。

## 定期実行

タスクスケジューラで `deploy.ps1`。抽選開始は 16時／18時 が多いので、
日中は1時間おき程度が妥当。走査は3ショップ×数ページで1分弱。
